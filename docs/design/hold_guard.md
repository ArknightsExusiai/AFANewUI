# 按住去重（HoldGuard）与「同时按键」故障链

> AGENTS.md 参考资料分册。改热键按住语义、`PureKeyWait`、`KeyForward` 透传状态、或排查「某键按了没反应 / 另一个键按住时本键失灵」时读本文件。
> 机制主体在 [key_designs_hotkey.md](key_designs_hotkey.md)；本文件专记**按住周期**这一件事的模型、历史故障链与已被推翻的假说。

## 1. 要解决的问题：一个键的按住状态，不能让别的键陪葬

旧实现用 `PureKeyWait`（= `while !KeyWait(pureKey, "T3")`）实现「按住热键时动作只触发一次」：动作跑完后把**热键线程一直挂住**，靠 `#MaxThreadsPerHotkey` 默认值 1 让同键的自动重复 down 被静默丢弃。

这个做法有三个结构性缺陷，全部已在生产日志与 issue 中复现：

| # | 缺陷 | 后果 |
|---|------|------|
| 1 | 线程寿命 = 用户按住时长（无上界） | AHK 同优先级线程是**协作式**的：被中断的线程在内层线程结束前不会恢复。按住 A 时按 B，B 的 `PureKeyWait` 成为当前线程，**A 的 `KeyWait` 被冻结、看不到 A 的物理松开** → A 的线程永不结束 → A 的 down 全被 `MaxThreadsPerHotkey` 挡掉 → **A 的功能失效，直到 B 松开**。这是 issue #286 的完整链条。 |
| 2 | 抬起信号可能永远不来 | 设备/驱动层吞掉 key-up 时，OS 与钩子的物理态都恒为「按下」，`KeyWait` 无任何路径返回 → 线程永久挂起 → 累计 `#MaxThreads`(10) 个卡住的动作线程后**所有热键都无法启动**。 |
| 3 | 打断者占线程会放大时序误差 | 被中断线程里的 `USleep` 是冻结的，恢复即到期 → 该 sleep 的剩余时间被吃掉，后续 Send 整体后移。日志实证：`USleep(50)` 实测 382ms / 3021ms（内层线程活多久就超时多久）。 |

**结论**：任何「以用户按键时长决定线程寿命」的等待都必须消灭，而不是调参。

## 2. 新模型：按住去重状态机

把「按住周期」从**线程寿命**改成**状态**：

| 项 | 职责 |
|---|---|
| `HoldGuard.TryBegin(pureKey)` | 动作入口调用。返回 true = 该键仍在上一个按住周期内，本次 down（键盘自动重复）应忽略；返回 false = 新按住周期，调用方继续执行动作 |
| `HoldGuard.RegisterTail(pureKey, fn)` | 注册「按住周期结束时的收尾回调」。带松开尾部的动作（如模拟左键点击的 `{LButton Up}`）用它替代原来挂在 `PureKeyWait` 之后的尾部 |
| `HoldGuard.EndHoldMs(pureKey)` | 物理抬起时由 `X Up` 变体调用：结束按住周期 + 执行尾部。**这是正常路径，毫秒级，不经过定时器** |
| `HoldGuard._Poll()` | 兜底定时器回调：①物理态校验 ②物理态跳变自愈 ③执行因兜底而触发的尾部 |

### 2.1 结束按住周期的三条路径与优先级

1. **事件驱动（正常）**：物理抬起 → 钩子回调 → `X Up` 变体 → 立刻结束按住周期 + 发尾部。延迟 1~2ms。
   唯一可能的延迟来源：此刻有别的动作线程处于 `Critical`（只有过帧三件套），Up 事件被缓冲到它结束——几十 ms，属既有设计。
2. **物理态校验（兜底）**：定时器读 `GetKeyState(pureKey, "P")`，显示已抬起即结束按住周期。覆盖「钩子被系统摘除」等 Up 变体收不到的场景。
3. **跳变自愈（兜底）**：定时器维护每个处于按住周期的键的物理态，看到 **down→up→down 跳变**即判定「上一次抬起事件丢了」，复位按住周期让新的按下能正常触发。
   判据只用**跳变次序**，不含任何时长阈值——不用「按了多久算新按下」这种时长假设，所以不会误伤真长按。

### 2.2 为什么不做「硬上限」

> **决策（2026-09-29，用户拍板）**：不设「按住超过 X 秒强制结束按住周期」。

代价已明确接受：若物理态长期显示按下**且**再无 down→up→down 跳变（即该键从此不再被按），按住周期常驻，**该键**不再触发。收益是不引入时长假设：真长按（按住左键拖拽等）永远不会被误切断。

这与旧实现的差别是量级性的：旧模型下同一个故障会让**线程额度枯竭 → 全键盘失效**；新模型下最坏情况只损失**这一个键**，且它不影响任何其他键。

### 2.3 状态与字段

| 字段 | 语义 |
|---|---|
| `_Holds` (Map, CaseSense=false) | `pureKey → {tick}`，`tick` 是本按住周期的**进入时刻**（也是「按住时长」日志的唯一来源） |
| `_Tails` (Map) | `pureKey → fn`，按住周期结束时执行的收尾回调 |
| `_PhysDown` (Map) | `pureKey → true/false`，定时器最近一次看到的物理态，用于跳变检测 |
| `_ClosedTick` (Map) | `pureKey → tick`，最近一次**由兜底路径**关闭按住周期的时刻，用于抑制迟到到达的物理 up（见 2.5） |

键名规范与 `KeyForward.PureKeyName` 一致（`StrLower(GetKeyName(...))`），Map 关闭大小写敏感。

### 2.4 定时器形态

| 参数 | 取值 | 理由 |
|---|---|---|
| 数量 | 单根常驻 | 处于按住周期的键绝大多数时间为空，空转只做一次 `Map.Count` 判断；「有按住周期就一定有兜底」成为结构保证，不需要在每次置位时管理注册/注销（也避开 `SetTimer` 函数对象身份陷阱） |
| 间隔 | 固定 300ms，独立常量 | 正常路径不经过定时器（`X Up` 变体毫秒级收尾），定时器只覆盖「Up 变体没到 / 钩子被系统摘除」，多等一个周期可接受；更小间隔只让兜底更快，代价是主线程每秒多几十次唤醒（AHK 定时器还受系统 tick 限制，小于约 10ms 的周期并不能稳定兑现）。跟 `TimingService._CurrentDelay` 走会让高帧档徒增跳数与主线程争用，同样不取。**代价已接受**：跳变自愈与兜底收尾的判定粒度同为 300ms，窗口内走完的 down→up→down 采样不到 |
| 每跳成本 | 空集合：一次 `Map.Count`；非空：每个处于按住周期的键一次 `GetKeyState` | 微秒级，可忽略 |

### 2.5 边界：抬起只是「迟到」而不是「丢失」

定时器可能先按物理态清了按住周期并发了尾部，随后真正的 `X Up` 变体才到达。此时 `KeyForward.InterceptedKeys` / `DownHandled` 已被清空，若无保护，Up 变体可能给游戏补发一个多余的 up。

处理：`KeyForward.ActionUpForward` 在补发前查 `HoldGuard.WasClosedByFallback(pureKey)`——该键的按住周期已由兜底路径收尾过，则跳过本次补发并记 INFO（`迟到抬起`）。

## 3. 旧模型的历史故障链（2026-02 → 2026-09）

排查时反复被重新怀疑的几个点，按时间顺序留档，避免重走：

| 时间 | 提交 | 发生了什么 |
|---|---|---|
| 2026-02-12 | `f63f22b` | `USleep` 是纯忙等（无任何让步）+ `ProcessSetPriority "Realtime"`。动作序列里的 `USleep` 期间钩子回调进不来 |
| 2026-02-13 | `e7a0f83` | 引入 `PureKeyWait`（当时只是把 `KeyWait(ThisHotkey)` 换成 `KeyWait(PureKeyName)`，修修饰符解析）。**注意：它不是阻塞源，从诞生起就是可中断的 `KeyWait`** |
| 2026-02-13 | `94ba64c` / `b73bc4d` | 修 `USleep`：循环内加 `DllCall("Sleep", 1)` 让步；优先级 Realtime → High |

| 2026-09-01 | `4df6701` | `PureKeyWait` 改分段 `KeyWait("T3")` 并加日志（**语义仍是无限等待**） |

| 2026-09-29 | 机制复现 | 用户复现「按住 f 再按 d → f 失效直到松开 d」；本文件第 1 节表内第 1 行的机制确认 |

### 3.1 issue #286 实测时间线（v1.9.3，2026-08-19 报）

issue 原文只记到「`USleep` 超时 382ms」，2026-09-29 的复现补全了后半段：

````
10:50.928  ActionPressPause 执行，key=f      ← 进入 PureKeyWait("f")，f 的线程挂住
10:51.503  ActionGameSpeed 执行，key=d      ← d 成为当前线程，f 的 KeyWait 被冻结
~10:53.1   透传 key=f（按住 2266ms）          ← f 物理松开，但 f 的 KeyWait 看不到
10:53.928  透传 key=f（按住 3000ms）          ← 用户再按 f，down 被 MaxThreadsPerHotkey 挡掉
…          透传 key=f（3610/4281/4969ms…）    ← 每次新按下都只补发 up，功能一次都没执行
10:54.549  等待物理松开已 3.0s：key=d        ← d 的 KeyWait 第一次超时（d 仍被按住）
10:58.108  透传 key=d（按住 6594ms）          ← d 松开，d 的线程结束
10:58.736  ActionPressPause 执行，key=f      ← f 立刻恢复
````

两个次生现象：

- `透传 key=f（按住 Xms）` 里的 X 读的是 `KeyForward._LastForwardDownTick`，它被每次新按下刷新 → 卡死期间这个数**不是**「本次按住时长」。该字段只服务「Up 补发回环」检测，「按住时长」必须由按住周期起始 tick 给出。
- 卡死期间**所有**其他热键的实际响应都被压到当前线程那个 `KeyWait` 每 3s 超时的一瞬间。

## 4. 已证伪的假说（不要重复验证）

| 假说 | 实测结论 | 证据 |
|---|---|---|
| 「`PureKeyWait` 一直占着线程，所以别的热键根本不能触发」 | **不成立**。处于可中断等待的线程不阻止其他热键启动线程 | 实测：一个线程停在 `WinWait` / `Sleep 3000` / 忙等时，第三个热键均正常触发并完整执行；`misc/Threads.htm` 明确 "While the function is in a waiting state, new threads can be launched" |
| 「旧版本的 `PureKeyWait` 是忙等」 | **不成立**。它从 `e7a0f83` 起就是 `KeyWait` | `git log -S` 全历史只有 `KeyWait` 一种实现 |
| 「`KeyWait` 属于无害等待」 | **不成立**。它会**连同所在线程一起被冻结**，从而看不到自己那个键的松开 | 本文第 1 节表内第 1 行、第 3.1 节时间线 |
| 「兜底定时器放在持有按住周期的线程里轮询 `GetKeyState` 就够了」 | **不成立**。该线程被挂起时轮询同样不会运行，与 `KeyWait` 是同一个坑 | 只有跑在**别的线程**上的代码（`SetTimer` 回调、其他热键回调）才能观测到状态变化 |
| 「`Sleep -1` / 可中断等待能避免被中断线程的时序漂移」 | **不成立**。被中断线程在内层线程结束前一律不恢复，换哪种等待都一样 | 实测 `DllCall("Sleep",1)` 与 `Sleep -1` 两条路径的外层 `USleep(50)` 都被拉长到约 3020ms |
| 「用注入事件可以构造物理长按来做自动化测试」 | **不成立**。AHK/Windows 在更新物理键态与热键判定时忽略注入事件 | 三次实测：`Send` / `keybd_event` 注入的 down 都不会让 `KeyWait` 进入等待（立即返回 1） |

## 5. 观测与判读

- **日志**：按住周期活跃时每 3s 一条节流 INFO（`按住周期：key=X 已按住 Ns`）。正常长按只留 INFO；WARN 收窄为「**物理态已抬起但按住周期未结束**」这类结构性异常——不再把「长按 30s」当异常报。
- **日志与 `HoldGuard.Snapshot()`**：`hold=[key+Ns(phys=down/up) …]` 给出此刻哪些键处于按住周期、已持续多久、物理态如何。按住周期常驻时这里会一直显示该键 —— 这是**预期行为**（第 2.2 节），不是线程泄漏。按住周期活跃时每 3s 一条节流 INFO。
- **判读顺序**（配合 [input_stall_diagnosis.md](input_stall_diagnosis.md)）：先看 `hold`（有没有按住周期没释放）→ 再看 `HoldGuard` 的兜底 WARN 与 `KeyForward` 等待物理松开日志。

## 7. 与快照其余字段的关系

- **`depth` 不再会因为「用户按住某个键」而长期非零**：除非动作本身很长，否则按住周期活跃期间 `depth` 应回落到 0。若 `depth` 长期不动且 `inflight` 有内容，那才是真正的动作线程泄漏。
